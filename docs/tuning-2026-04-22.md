# Tuning Notes - 2026-04-22

## Why these tuning passes happened

Dry-run review exposed several false positives caused by broad keyword matching, especially when structural classification looked at message body content.

Observed issues included:
- Google security mail incorrectly labeled as opportunities
- newsletters incorrectly labeled as finance
- promotional mail incorrectly labeled as shipping
- neutral announcements incorrectly labeled as calendar or opportunities
- some logistics mail classified as generic services instead of shipping
- some obvious commercial/promotional mail left in review
- generic Google developer mail treated as too important
- opportunity workflow labels sometimes too aggressive

## First fixes applied

### 1. Structural classification narrowed to sender + subject
Structural classification now uses sender and subject only.

This applies to:
- finance
- shipping
- calendar
- opportunities
- commercial classification

Body text remains available only for workflow inference (`to respond`, `FYI`, `notification`).

### 2. Strong sender overrides added
Default overrides now include:
- forced important: Google account security, incident status
- forced commercial: Qwertee, Steam, StackCommerce, Telecompaper, Substack, TLDR, Netflix, Bandsintown, Ticketmaster
- forced review: LinkedIn newsletter sender

### 3. Regexes tightened
Patterns were narrowed substantially:
- finance only strong transactional phrases
- shipping only strong logistics phrases
- calendar only explicit invite/update phrases
- opportunities now depend on stronger subject terms and sender weighting

### 4. Important Google security handling improved
Google account/security mail should now fall into:
- `Important/Services`
- usually `3: notification`

## Second fixes applied

### 5. Shipping sender overrides
Added explicit shipping sender handling for:
- `post.at`
- `meinesendung@post.at`
- `amazon.de`
- `notice.aliexpress.com`

This should move logistics mail away from generic services and into:
- `Important/Shipping`
- `3: notification`

### 6. Opportunity invite handling
Interview-style mail now prefers:
- `Important/Opportunities`
- `1: to respond`

### 7. More commercial sender overrides
Added more explicit commercial senders for messages that were still falling into review.

## Final light tuning pass

### 8. Reduced generic Google/service overreach
Generic Google developer mail is now routed to review rather than treated as an important service by default.

### 9. Added calendar sender overrides
Important known calendar-style senders can now route directly to:
- `Important/Calendar`
- `1: to respond`

### 10. Softened some opportunity workflow handling
Opportunity senders like LinkedIn jobs, XING jobs, and Experteer now default more gently when appropriate, instead of pushing everything toward `to respond`.

### 11. Improved Phase 3 digest usefulness
Digest sections are now organized around:
- Needs response
- Important notifications
- Opportunities
- Review later

They are also deduplicated and sorted by recency.

## Additional tuning from live log review

### 12. Commercial leakage from review reduced
Log review showed several obvious commercial items still landing in `Review/Ambiguous`, including:
- Booking.com rental-car promotion
- Kompas Shop shipping-free promo
- XING news digests
- karriere.at job recommendation digest
- Universal Music promo mail
- Kickstarter project updates
- LinkedIn social-notification mail
- XING birthday/social mail

To reduce that leakage, the config now adds:
- more explicit `forceCommercialSenders`
- stronger ad/newsletter/campaign subject patterns

### 13. Opportunity coverage improved
Log review also showed at least one obvious job lead from `jobs-noreply@linkedin.com` landing outside the opportunity bucket.

The classifier now:
- treats `jobs-noreply@linkedin.com` and `job.karriere.at` as opportunity senders
- recognizes stronger opportunity subjects like `apply to ... role`, `actively recruiting`, and German `Job-Empfehl...`
- still keeps alert-style sources like LinkedIn job alerts and Experteer gentler by default where appropriate

### 14. Digest no longer depends only on already-labeled threads
The digest produced `No notable items.` even while DecisionLog clearly showed many important and reviewable messages.

To make digest output useful during dry-run validation, it now:
- searches a candidate inbox pool directly
- runs the current classifier on those threads
- builds sections from inferred decisions, not only existing Gmail labels
- shows section counts
- shortens sender display names
- shows an overflow line when a section contains more items than shown
